Continuous integration for the mining project

This revision adds GitHub Actions CI. It automatically tests changes on pushes and pull requests. It does not deploy to Databricks, run Azure jobs, provision resources or require Azure credentials. MLflow remains a separate optional experiment-tracking feature.

What changed

The notebooks now import shared logic from notebooks/mining_core.py. The same functions are tested by CI: clean_shifts, machine_summary, temporal_split and fit_model. This avoids testing a detached copy while your real notebook uses different rules. For this tiny dataset, validation, machine summaries and modelling run in Pandas/scikit-learn; Spark handles raw ingestion, Delta persistence and the daily SQL report.

Reimport the revised notebooks if you already imported the old ones. Also upload notebooks/mining_core.py as a normal Python file into the SAME Databricks Workspace folder as the four notebooks. In Workspace, use the folder Import/Upload option for files. Do not create a table from this Python file and do not put it in the data volume. It has no Databricks notebook header so it remains an ordinary module. In the supplied notebook configurations, keep the same catalog/schema. If the import fails, check mining_core.py is beside the notebook; restart Python after changing a previously imported module, then run cells from the beginning.

What runs automatically

1. GitHub checks out your commit.
2. It selects Python 3.11 and installs the pinned requirements-ci.txt dependencies.
3. It parses all four notebooks to catch Python syntax errors and checks that committed code cells have no saved outputs.
4. It runs 13 unittest tests, including the exact supplied-data counts, all six rejected IDs, reference clean data, conflicting duplicates, numeric infinity, availability boundaries, weighted energy ratios, report reconciliation, chronological separation, outcome-feature exclusion, model fitting and future scoring.
5. A nonzero test exit makes the workflow fail. A green run means these checks passed for that commit.

No Spark, Delta, Unity Catalog, permission, Azure-network or live MLflow execution occurs on the runner. A green CI result is not a successful Databricks run. Run the notebooks in your workspace to verify those integrations. The static notebook check parses Python; it does not execute notebook cells or validate SQL strings. CI does not automatically protect main or prevent merging until you enable the repository rule below.

Step 1 create the GitHub repository

Sign in to GitHub. Select + → New repository. Name it mining-throughput-databricks. Choose Private for personal practice. Do not enable any setting that exposes credentials. Create the repository with a README so a main branch exists.

Extract the revised ZIP locally. The repository root must contain START_HERE.html, requirements-ci.txt, notebooks, data, tests, scripts, and .github. Do not upload the ZIP itself or place all these inside another Mining_Throughput_Project folder in the repository. The required workflow path at repository root is .github/workflows/ci.yml.

Browser-only route: Add file → Upload files. Upload the contents of Mining_Throughput_Project, preserving directories, and commit to main. Hidden .github folders may be omitted by your operating system or browser. To guarantee the workflow is present, use Add file → Create new file; enter .github/workflows/ci.yml and paste the supplied ci.yml contents, then commit. If it already exists, do not create a second workflow. Verify notebooks/mining_core.py and tests/test_project.py exist at the expected paths.

Alternatively use VS Code Source Control or these commands from inside the extracted Mining_Throughput_Project directory. Replace YOUR_USERNAME with your actual GitHub username:

git init
git add .
git commit -m "Add Databricks mining project with CI"
git branch -M main
git remote add origin https://github.com/YOUR_USERNAME/mining-throughput-databricks.git
git push -u origin main

For this command-line route, create an empty GitHub repository without a README first to avoid an unrelated initial history. Use GitHub browser authentication, GitHub CLI or a credential manager if Git asks you to sign in; do not put a password/token in a repository URL or file.

Step 2 inspect your first CI run

Open repository → Actions → Mining project CI. Open the newest run for your commit → Validate mining project. Expand Install CI dependencies, Check notebook Python syntax and Test shared project logic and supplied data. Expect notebook syntax confirmations and 13 tests with OK.

If Actions is disabled, enable it in the repository Actions settings if permitted. If your organisation blocks hosted runners, third-party actions or private-repository minutes, follow the account policy and check billing/runner availability. This CI uses GitHub-hosted CPU runners, not Azure Databricks compute. No Databricks secrets or service connections are needed.

You can also start a run using Actions → Mining project CI → Run workflow once the workflow is on the default branch. The supplied YAML triggers every push and pull request; it does not filter to a specific branch. Pushing to a branch with an open pull request can produce separate push and pull-request runs.

Step 3 see a deliberate failure

1. In GitHub create a new branch named practice-ci-failure from main.
2. Open notebooks/mining_core.py → Edit. Change x.prior_shift_availability.between(0,1) to x.prior_shift_availability.between(0,1.1). Commit on the practice branch. This deliberately admits an impossible availability value of 1.01.
3. Open a pull request from practice-ci-failure to main. Watch Actions or the PR Checks tab. The boundary test must fail because 1.01 was accepted. Do not change the test to hide the defect.
4. On the same branch restore between(0,1), commit and wait for the new run. All 13 tests should pass again.
5. Review the diff. You can close the PR because the final code equals main, or use a separate useful improvement for a meaningful merge. Keep screenshots of red and green checks for your learning notes.

Step 4 optionally require CI before merge

Repository Settings → Rules → Rulesets, or Branches → branch protection if your account uses that interface. Target main, require a pull request, and require the Validate mining project status check after it has run once. GitHub may display the workflow/job combination in the selector; choose the check generated by this workflow. Feature availability depends on your repository visibility and plan. If unavailable, use checks as a manual review rule; do not claim main is protected.

Optional local execution

From repository root use Python 3.11 in a virtual environment, then:

python -m pip install -r requirements-ci.txt
python scripts/check_notebooks.py
python -m unittest discover -s tests -v

These commands reproduce the CI checks without Azure. The Databricks requirements.txt remains a range-based environment guide; requirements-ci.txt pins the three top-level CI libraries. Transitive dependencies and the hosted runner image are not fully locked, so this is not a bit-for-bit reproducible environment. Do not install the CI pins over a functioning Databricks runtime just to match the runner.

Finish in Databricks

GitHub and your manually imported Workspace files are separate copies. CI does not synchronise them. After reviewing a passing change, manually update the corresponding Workspace mining_core.py/notebooks, restart Python if needed and rerun your personal lab. That is a manual update, not CD. Keep the raw datasets in the Unity Catalog volume. Reruns overwrite only your named practice output tables.
